# Getting started

[← Helm charts](../README.md)

This guide gets Rush running on a development cluster, explains what Helm
creates, and shows the small set of values you usually change later.

## Before you install

The quick install needs Kubernetes 1.27 or newer, Helm 3.8 or newer, a default
StorageClass, and about 4 GiB of available memory. Check the cluster first:

```bash
kubectl version
helm version
kubectl get storageclass
```

The instructions use the `observability` namespace and a Helm release named
`rush`. Keep those names while following the guide. Resource and Secret names
shown below are based on them.

## Install a development stack

Run the [install command in the main README](../README.md#install-on-kubernetes). It makes
these choices for you:

| Setting | Choice | Why |
|---|---|---|
| ClickHouse | One StatefulSet with a 20 GiB volume | Fits a local or evaluation cluster and does not need the ClickHouse operator. |
| Query API | Development mode at `http://localhost:8080` | Allows browser login through `kubectl port-forward` without public DNS or TLS. |
| Logs | Vector DaemonSet | Sends Kubernetes container logs to Rush. |
| Metrics | metrics-agent with `env=dev` | Discovers Prometheus-style targets and remote-writes their metrics. |
| Traces and OTLP metrics | OpenTelemetry Collector | Provides OTLP gRPC and HTTP endpoints inside the cluster. |
| Passwords and ingest keys | Generated by Helm | Avoids putting secrets in commands or values files. |

Helm preserves generated secrets during upgrades.

## Check startup

List every Rush pod:

```bash
kubectl -n observability get pods
```

If a pod is still starting, inspect it by name:

```bash
kubectl -n observability describe pod <pod-name>
kubectl -n observability logs <pod-name> --all-containers
```

Run the chart's connectivity test after the deployments are ready:

```bash
helm test rush -n observability --logs
```

## Sign in

Forward the frontend Service:

```bash
kubectl -n observability port-forward svc/rush-frontend 8080:80
```

Leave that command running. Open [http://localhost:8080](http://localhost:8080)
and sign in with:

- Username: `admin`
- Password: the value returned by this command

```bash
kubectl -n observability get secret rush-bootstrap \
  -o jsonpath='{.data.initial-admin-password}' | base64 -d; echo
```

Change the generated password after the first login.

## Send traces from an application

Applications in the cluster can send OTLP to:

| Protocol | Endpoint |
|---|---|
| OTLP gRPC | `http://rush-otel-collector.observability.svc:4317` |
| OTLP HTTP | `http://rush-otel-collector.observability.svc:4318` |

The collector already has the generated Rush ingest key. Your application only
needs to send OTLP to the collector.

## Change the environment label

The quick install adds `env=dev` to metrics sent by metrics-agent. Change it
without replacing the rest of the release:

```bash
helm upgrade rush \
  oci://ghcr.io/rushobservability/helm-charts/rush-observability-stack \
  --namespace observability \
  --reuse-values \
  --set-string metricsAgent.extraLabels.env=staging
```

Use `--reuse-values` only for small changes to an existing release. Keep a
values file in Git before you move to production.

## Storage

The development install uses the cluster's default StorageClass and a 20 GiB
ClickHouse volume. To use another class or size, add these values to your own
values file:

```yaml
rush:
  clickhouseStandalone:
    persistence:
      storageClass: fast-ssd
      size: 100Gi
```

Changing a StatefulSet volume size later depends on the StorageClass and CSI
driver. Choose the production size before ingesting data you plan to keep.

## Move to production

Do not carry the development settings into production unchanged. At minimum:

1. Use an HTTPS hostname for the UI and Query API base URL.
2. Decide whether ClickHouse should use operator-managed or external mode.
3. Pin chart and container versions.
4. Store your values file and externally managed Secrets in your deployment
   system.
5. Review storage size, retention, backups, resource requests, ingress, and
   NetworkPolicies.

A small production values file can start like this:

```yaml
rush:
  queryApi:
    config:
      runtime:
        environment: production
        baseUrl: https://rush.example.com
    ingress:
      enabled: true
      className: nginx
      frontend:
        host: rush.example.com
        tls:
          enabled: true
          secretName: rush-tls
  clickhouse:
    enabled: true
    mode: operator

collectors:
  mode: hybrid

metricsAgent:
  enabled: true
  extraLabels:
    env: production
```

Install it with a pinned chart version:

```bash
helm upgrade --install rush \
  oci://ghcr.io/rushobservability/helm-charts/rush-observability-stack \
  --version 0.2.0 \
  --namespace observability \
  --create-namespace \
  --values values-production.yaml
```

Continue with the [ClickHouse](clickhouse.md),
[networking](networking.md), [security](security.md), and
[reliability](reliability.md) guides before using this in production.

## Remove the development install

```bash
helm uninstall rush -n observability
```

Helm does not delete persistent volume claims automatically. Delete the data
only when you no longer need it:

```bash
kubectl -n observability delete pvc -l app.kubernetes.io/instance=rush
```
